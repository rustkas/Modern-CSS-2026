# Глава 25. Построение дизайн-системы: от компонентов к инженерной платформе

> К этому моменту книги мы уже рассмотрели все основные технологии современного CSS: каскадные слои, дизайн-токены, контейнерные запросы, современные цветовые пространства, новые селекторы, анимации и механизмы изоляции.

Однако сами по себе технологии ещё не образуют дизайн-систему.

Настоящая дизайн-система возникает тогда, когда отдельные компоненты превращаются в единый инженерный продукт, которым пользуются десятки команд, а решения принимаются один раз и затем автоматически распространяются на всю кодовую базу.

Именно такой подход отличает современные дизайн-системы от обычных библиотек компонентов.

---

## 25.1 Единый источник истины

### Роль дизайн-токенов

Любая дизайн-система начинается с определения единственного источника истины (*Single Source of Truth*).

В современной архитектуре таким источником становятся дизайн-токены.

```text
Дизайн-токены
  ↓
Цветовая система
  ↓
Типографика
  ↓
Интервалы
  ↓
Радиусы
  ↓
Размеры
  ↓
Тени
  ↓
Продолжительность анимаций
  ↓
Уровни Elevation
```

**Все остальные уровни системы используют только токены, а не конкретные значения.**

### Пример: система токенов

```css
@layer tokens {
  :root {
    /* === Цвета === */
    --color-primary: oklch(65% 0.22 255);
    --color-primary-hover: color-mix(in oklch, var(--color-primary), white 15%);
    --color-surface: light-dark(white, #1a1a1a);
    --color-text: light-dark(#1a1a1a, white);
    
    /* === Типографика === */
    --font-family: system-ui, -apple-system, sans-serif;
    --font-size-sm: 0.875rem;
    --font-size-base: 1rem;
    --font-size-lg: 1.125rem;
    --font-size-xl: 1.25rem;
    --font-size-2xl: 1.5rem;
    
    /* === Интервалы === */
    --space-xs: 0.25rem;
    --space-sm: 0.5rem;
    --space-md: 1rem;
    --space-lg: 1.5rem;
    --space-xl: 2rem;
    --space-2xl: 3rem;
    
    /* === Радиусы === */
    --radius-sm: 4px;
    --radius-md: 8px;
    --radius-lg: 12px;
    --radius-xl: 16px;
    --radius-full: 9999px;
    
    /* === Тени === */
    --shadow-sm: 0 1px 2px rgba(0,0,0,0.05);
    --shadow-md: 0 4px 12px rgba(0,0,0,0.08);
    --shadow-lg: 0 8px 24px rgba(0,0,0,0.12);
    --shadow-xl: 0 16px 48px rgba(0,0,0,0.16);
    
    /* === Анимации === */
    --duration-fast: 0.15s;
    --duration-medium: 0.3s;
    --duration-slow: 0.5s;
    --easing-standard: ease;
    --easing-spring: cubic-bezier(0.34, 1.56, 0.64, 1);
  }
}
```

**Это позволяет изменять оформление всей системы через изменение ограниченного набора параметров.**

## 25.2 Архитектура компонентов

### От токенов к компонентам

После определения токенов строится библиотека компонентов.

Каждый компонент представляет собой самостоятельный модуль, обладающий:

```text
Собственным API
  ↓
Custom Properties, data-атрибуты
  ↓
Собственной областью ответственности
  ↓
Один компонент — одна задача
  ↓
Встроенной адаптивностью
  ↓
Container Queries, логические свойства
  ↓
Поддержкой доступности
  ↓
:focus-visible, ARIA, prefers-reduced-motion
  ↓
Минимальным количеством публичных настроек
  ↓
Чем меньше API, тем проще поддержка
```

### Пример: компонент с чётким API

```css
@layer components {
  .button {
    /* Публичный API через Custom Properties */
    --button-bg: var(--color-primary);
    --button-color: var(--color-text-inverse);
    --button-padding: var(--space-md) var(--space-lg);
    --button-radius: var(--radius-md);
    
    /* Базовая структура */
    display: inline-flex;
    align-items: center;
    justify-content: center;
    gap: var(--space-xs);
    padding: var(--button-padding);
    background: var(--button-bg);
    color: var(--button-color);
    border: 1px solid transparent;
    border-radius: var(--button-radius);
    cursor: pointer;
    
    /* Состояния */
    &:hover {
      background: color-mix(in oklch, var(--button-bg), white 15%);
    }
    
    &:focus-visible {
      outline: 2px solid var(--color-primary);
      outline-offset: 2px;
    }
    
    /* Варианты через data-атрибуты */
    &[data-variant="primary"] {
      --button-bg: var(--color-primary);
    }
    
    &[data-variant="danger"] {
      --button-bg: var(--color-danger);
    }
    
    /* Размеры */
    &[data-size="sm"] {
      --button-padding: var(--space-sm) var(--space-md);
      font-size: var(--font-size-sm);
    }
    
    &[data-size="lg"] {
      --button-padding: var(--space-lg) var(--space-xl);
      font-size: var(--font-size-lg);
    }
    
    /* Адаптивность */
    @container (max-width: 400px) {
      width: 100%;
    }
  }
}
```

### Взаимодействие компонентов

Компоненты взаимодействуют с системой через:

```text
CSS Custom Properties
  ↓
Настройка извне
  ↓
data-атрибуты
  ↓
Варианты и состояния
  ↓
Современные псевдоклассы
  ↓
:hover, :focus-visible, :disabled
  ↓
Документированные состояния
  ↓
[data-state="loading"]
```

**Такой подход позволяет независимо развивать каждый компонент без нарушения совместимости всей библиотеки.**

## 25.3 Управление темами

### Поддержка нескольких тем

Современная дизайн-система редко ограничивается единственной цветовой схемой. Как правило, она поддерживает несколько тем оформления.

```text
Светлая тема
  ↓
Тёмная тема
  ↓
Высококонтрастная тема
  ↓
Брендированные темы
```

### Инструменты для тем

Для этого используются возможности современного CSS:

```text
Custom Properties
  ↓
Динамические значения
  ↓
light-dark()
  ↓
Автоматическая адаптация
  ↓
Relative Color Syntax
  ↓
Изменение каналов
  ↓
color-mix()
  ↓
Смешивание цветов
  ↓
@property
  ↓
Типизированные свойства
```

### Пример: система тем

```css
@layer tokens {
  /* Базовые токены */
  :root {
    color-scheme: light dark;
    
    --color-surface: light-dark(
      oklch(98% 0.01 100),
      oklch(18% 0.01 100)
    );
    
    --color-text: light-dark(
      oklch(20% 0.01 100),
      oklch(90% 0.01 100)
    );
    
    --color-primary: oklch(65% 0.22 255);
  }
  
  /* Тёмная тема через prefers-color-scheme */
  @media (prefers-color-scheme: dark) {
    :root {
      color-scheme: dark;
    }
  }
  
  /* Высококонтрастная тема */
  @media (prefers-contrast: high) {
    :root {
      --color-primary: oklch(50% 0.25 255);
      --color-surface: light-dark(
        oklch(100% 0 0),
        oklch(0% 0 0)
      );
      --color-text: light-dark(
        oklch(0% 0 0),
        oklch(100% 0 0)
      );
    }
  }
  
  /* Ручное переключение темы */
  [data-theme="dark"] {
    color-scheme: dark;
    --color-surface: oklch(18% 0.01 100);
    --color-text: oklch(90% 0.01 100);
  }
  
  [data-theme="light"] {
    color-scheme: light;
    --color-surface: oklch(98% 0.01 100);
    --color-text: oklch(20% 0.01 100);
  }
}
```

**Это позволяет описывать темы декларативно, без дублирования большого объёма CSS.**

### Учёт поддержки браузеров

ри использовании новых возможностей платформы важно учитывать их текущий статус Baseline и предусматривать резервные варианты там, где это необходимо.

> **Применительно к `light-dark()`, использованному выше:** функция находится в статусе Baseline **Newly available** с мая 2024 года (поддерживается всеми core-браузерами: Chrome/Edge 123+, Firefox 120+, Safari 17.5+), но порог **Widely available** — то есть завершение 30-месячного периода — наступает только 13 ноября 2026 года. До этой даты формально сохраняется вероятность столкнуться с пользователями на чуть более старых версиях браузеров (особенно корпоративные сборки и iOS/iPadOS с задержкой обновлений), и фолбэк ниже — не столько избыточная предосторожность, сколько обоснованная практика для систем с широкой аудиторией вплоть до конца 2026 года. После этой даты проверку можно будет убрать.

```css
/* Проверка поддержки light-dark() */
@supports (color: light-dark(white, black)) {
  .theme-aware {
    color: light-dark(black, white);
  }
}

@supports not (color: light-dark(white, black)) {
  .theme-aware {
    color: black;
  }
}
```

## 25.4 Масштабирование системы

### Проблемы роста

По мере роста проекта возрастает не только количество компонентов, но и количество команд, работающих над ними.

```text
Небольшой проект
  ↓
1-2 разработчика
  ↓
10-20 компонентов
  ↓
Крупный проект
  ↓
10+ команд
  ↓
100+ компонентов
```

### Архитектурные соглашения

Поэтому особую роль начинают играть архитектурные соглашения.

**Cascade Layers**

Разделяют ответственность между уровнями:

```css
@layer reset, tokens, base, patterns, components, utilities, overrides;
```

```text
reset → нормализация браузерных стилей
  ↓
tokens → дизайн-токены
  ↓
base → базовые HTML-элементы
  ↓
patterns → повторяемые шаблоны
  ↓
components → UI-компоненты
  ↓
utilities → атомарные классы
  ↓
overrides → исключения
```

**Изоляция компонентов**

В зависимости от характера проекта могут использоваться:

```text
@scope
  ↓
Локальный каскад (CSS)
  ↓
CSS Modules
  ↓
Уникальность имён (сборка)
  ↓
Shadow DOM
  ↓
Полная инкапсуляция (браузер)
```

Каждый механизм решает собственную задачу и выбирается исходя из требований конкретной архитектуры.

**Container Queries**

Позволяют компонентам оставаться независимыми от конкретного макета страницы.

```css
.component {
  container-type: inline-size;
}

@container (max-width: 400px) {
  .component {
    /* Адаптация к контейнеру */
  }
}
```

**Именно автономность компонентов становится одной из важнейших характеристик современной дизайн-системы.**

## 25.5 Документация как часть продукта

### Почему документация важна

Дизайн-система существует только тогда, когда ею могут пользоваться другие разработчики. Поэтому документация становится частью самой системы.

```text
Без документации
  ↓
Разработчики не знают, как использовать
  ↓
Создают свои компоненты
  ↓
Дизайн-система не используется
  ↓
С документацией
  ↓
Разработчики понимают, как использовать
  ↓
Используют существующие компоненты
  ↓
Дизайн-система живёт
```

### Что должна включать документация

Обычно она включает:

```text
Описание компонентов
  ↓
Что делает компонент
  ↓
Публичный API
  ↓
Custom Properties, data-атрибуты
  ↓
Варианты использования
  ↓
Примеры кода
  ↓
Рекомендации по доступности
  ↓
ARIA, фокус, prefers-reduced-motion
  ↓
Ограничения
  ↓
Когда не использовать компонент
  ↓
Сведения о поддержке браузеров
  ↓
Baseline статус
```

### Storybook как инструмент

Практика показывает, что «живая» документация, автоматически собираемая из исходного кода (например, с помощью Storybook), значительно устойчивее ручных описаний, которые быстро устаревают.

```javascript
// Button.stories.js
export default {
  title: 'Components/Button',
  component: Button,
  argTypes: {
    variant: {
      control: 'select',
      options: ['primary', 'danger', 'outline'],
    },
    size: {
      control: 'select',
      options: ['sm', 'md', 'lg'],
    },
  },
};

export const Primary = {
  args: {
    variant: 'primary',
    children: 'Кнопка',
  },
};

export const Loading = {
  args: {
    variant: 'primary',
    children: 'Загрузка...',
    state: 'loading',
  },
};
```

### Документирование CSS API

```css
/**
 * Button — основной компонент для действий пользователя
 * 
 * @tokens
 * --button-bg - Цвет фона (default: var(--color-primary))
 * --button-color - Цвет текста (default: var(--color-text-inverse))
 * --button-padding - Внутренние отступы (default: var(--space-md) var(--space-lg))
 * --button-radius - Скругление (default: var(--radius-md))
 * 
 * @variants
 * [data-variant="primary"] - Основная кнопка
 * [data-variant="danger"] - Кнопка опасного действия
 * [data-variant="outline"] - Кнопка с обводкой
 * 
 * @sizes
 * [data-size="sm"] - Маленькая
 * [data-size="lg"] - Большая
 * 
 * @states
 * [data-state="loading"] - Состояние загрузки
 * 
 * @accessibility
 * - Поддерживает :focus-visible
 * - Поддерживает prefers-reduced-motion
 * - Правильный цветовой контраст
 */
.button { ... }
```

## 25.6 Эволюция дизайн-системы

### Постоянное развитие

Ни одна дизайн-система не остаётся неизменной. Развитие веб-платформы требует постоянного пересмотра архитектурных решений.

```text
Веб-платформа развивается
  ↓
Появляются новые возможности CSS
  ↓
Дизайн-система должна обновляться
  ↓
Нужна стратегия развития
```

### Стратегия внедрения новых возможностей

Полезно разделять новые возможности CSS на три категории:

| Статус | Практика |
|--------|----------|
| **Baseline Widely available** | Можно использовать без ограничений |
| **Baseline Newly available** | Применять как прогрессивное улучшение |
| **Экспериментальные возможности** | Использовать только после проверки через `@supports` и с резервным вариантом |

### Пример: внедрение новой возможности

```css
/* 1. Проверка поддержки через @supports */
@supports (container-type: inline-size) {
  .component {
    container-type: inline-size;
  }
}

/* 2. Базовый вариант для всех браузеров */
.component {
  display: block;
}

/* 3. Улучшение для поддерживающих браузеров */
@supports (container-type: inline-size) {
  @container (max-width: 400px) {
    .component {
      display: grid;
      grid-template-columns: 1fr;
    }
  }
}
```

### Управление версиями

```text
v1.0.0 — первая версия
  ↓
v1.1.0 — добавлены новые компоненты
  ↓
v1.2.0 — добавлены новые возможности
  ↓
v2.0.0 — breaking changes
  ↓
Миграция
  ↓
Обновление всех проектов
```

**Такой подход позволяет постепенно внедрять новые возможности платформы без нарушения стабильности существующих проектов.**

## 25.7 Итоги книги

### От языка к платформе

Современный CSS перестал быть языком оформления отдельных страниц. Сегодня он представляет собой зрелую инженерную платформу, позволяющую проектировать масштабируемые интерфейсы с помощью декларативных механизмов, встроенных непосредственно в браузер.

```text
CSS 2.1 → язык оформления
  ↓
CSS 3 → адаптивность
  ↓
CSS 2015-2020 → препроцессоры, методологии
  ↓
CSS 2026 → инженерная платформа
```

### Ключевые изменения

Каскадные слои устраняют конфликты приоритетов:

```text
Специфичность → @layer
```

Контейнерные запросы делают компоненты независимыми от размеров экрана:

```text
Media Queries → Container Queries
```

Современные цветовые пространства открывают новые возможности управления палитрой:

```text
sRGB, HSL → OKLCH, OKLab
```

Дизайн-токены превращают визуальные решения в программный интерфейс:

```text
Магические числа → Design Tokens
```

### Главная тенденция

```text
JavaScript и инструменты сборки
  ↓
Постепенный перенос возможностей
  ↓
Сам язык CSS
  ↓
Всё больше задач решается декларативно
  ↓
Средствами платформы
  ↓
Без дополнительного кода
  ↓
И без сложной инфраструктуры
```

### Итог

Именно эта эволюция делает Modern CSS не просто очередной версией языка, а новой моделью проектирования пользовательских интерфейсов, в которой ключевую роль играют предсказуемость, масштабируемость и долгосрочная поддерживаемость кодовой базы.
