# Глава 22. Современные стратегии оптимизации CSS

> Современная производительность CSS определяется не отдельными «магическими» свойствами, а архитектурой интерфейса. Большинство проблем возникает не из-за медленного браузера, а из-за того, что приложение заставляет его выполнять слишком много лишней работы: пересчитывать стили, заново раскладывать документ, повторно рисовать пиксели или создавать избыточные композитные слои.

Если глава 21 объясняла устройство Rendering Pipeline, то здесь рассматриваются практические приёмы, позволяющие минимизировать нагрузку на каждую его стадию.

Главный принцип современной оптимизации можно сформулировать так:

> **Лучше предотвратить дорогостоящие вычисления, чем ускорять уже возникшую проблему.**

---

## 22.1 Оптимизация начинается с архитектуры

### Влияние структуры на производительность

Самое большое влияние на производительность оказывает вовсе не выбор отдельных CSS-свойств, а структура приложения.

Хорошо спроектированная архитектура предполагает:

```text
Независимые компоненты
  ↓
Локальная область действия стилей
  ↓
Минимальное количество взаимных зависимостей
  ↓
Небольшие области перерасчёта
```

### Инструменты современной архитектуры

Современные возможности CSS значительно упрощают такую архитектуру.

```text
@layer
  ↓
Архитектурное управление приоритетами
  ↓
@scope
  ↓
Локальный каскад
  ↓
Container Queries
  ↓
Адаптация к контейнеру, а не к вьюпорту
  ↓
Design Tokens
  ↓
Единый язык дизайна
  ↓
CSS Nesting
  ↓
Компонентная организация кода
```

**Именно они позволяют ограничить влияние изменений рамками отдельного компонента.**

### Пример: изолированный компонент

```css
@layer components {
  @scope (.product-card) {
    .product-card {
      container-type: inline-size;
      container-name: product;
      display: grid;
      gap: var(--space-md);
      
      /* Изменения внутри не влияют на страницу */
      & .title {
        font-size: var(--font-size-xl);
      }
      
      @container product (max-width: 400px) {
        grid-template-columns: 1fr;
      }
    }
  }
}
```

## 22.2 Ограничение области вычислений

### Принцип локализации

Не каждое изменение должно затрагивать всю страницу. CSS предоставляет несколько механизмов локализации работы браузера.

### contain — объявление независимости

Позволяет объявить компонент независимым.

```css
.widget {
  contain: content; /* layout + paint + style */
}

/* Браузер знает: изменения внутри .widget не влияют на внешнюю часть документа */
```

**На практике чаще всего используются:**

| Значение | Что изолирует |
|----------|---------------|
| `layout` | Геометрию элемента |
| `paint` | Отрисовку элемента |
| `style` | Стили элемента |
| `content` | layout + paint + style |
| `strict` | layout + paint + style + size |

```css
/* Изолируем карточку полностью */
.card {
  contain: strict;
}

/* Изолируем только layout и paint */
.widget {
  contain: layout paint;
}
```

**При правильном использовании браузер перестаёт пересчитывать соседние части документа.**

### content-visibility — пропуск рендеринга

Для длинных документов браузер способен полностью пропускать элементы, находящиеся далеко за пределами экрана.

```css
.article {
  content-visibility: auto;
}

.article-item {
  content-visibility: auto;
  contain-intrinsic-size: 200px; /* Резервируем место */
}
```

**Практически всегда следует использовать совместно с `contain-intrinsic-size`, чтобы избежать скачков Layout (CLS).**

```css
/* ✅ Хорошо — нет CLS */
.long-list-item {
  content-visibility: auto;
  contain-intrinsic-size: 300px 200px; /* height width */
}

/* ❌ Плохо — возможен CLS */
.long-list-item {
  content-visibility: auto;
}
```

## 22.3 Минимизация Layout

### Почему Layout — самая дорогая стадия

Layout остаётся самой дорогой стадией Rendering Pipeline. Поэтому современный CSS стремится уменьшить количество ситуаций, когда он вообще необходим.

```text
Layout
  ↓
Вычисление геометрии
  ↓
Рекурсивный обход DOM
  ↓
Зависит от вложенности
  ↓
★★★★★ самая дорогая
```

### Основные рекомендации

**1. Используйте Flexbox и Grid вместо абсолютного позиционирования**

```css
/* ✅ Хорошо — Flexbox */
.container {
  display: flex;
  justify-content: space-between;
}

/* ❌ Плохо — абсолютное позиционирование */
.container {
  position: relative;
}
.item {
  position: absolute;
  left: 0;
  top: 0;
}
```

**2. Применяйте `transform` вместо изменения размеров**

```css
/* ✅ Хорошо — только Composite */
.element:hover {
  transform: scale(1.1);
}

/* ❌ Плохо — Layout */
.element:hover {
  width: 110px;
  height: 110px;
}
```

**3. Используйте `aspect-ratio` для фиксированных пропорций**

```css
/* ✅ Хорошо — резервирование места */
.image {
  aspect-ratio: 16 / 9;
  width: 100%;
  object-fit: cover;
}

/* ❌ Плохо — CLS без резервирования */
.image {
  width: 100%;
}
```

**4. Избегайте постоянного изменения размеров элементов во время анимации**

```css
/* ✅ Хорошо — анимация Composite */
@keyframes expand {
  from { transform: scaleX(0); }
  to { transform: scaleX(1); }
}

/* ❌ Плохо — анимация Layout */
@keyframes expand-bad {
  from { width: 0; }
  to { width: 100%; }
}
```

### Container Queries — локализация Layout

Container Queries помогают локализовать изменения внутри компонента вместо перестройки всей страницы.

```css
.card-container {
  container-type: inline-size;
}

/* Изменения внутри контейнера не влияют на внешнюю часть */
@container (max-width: 400px) {
  .card {
    grid-template-columns: 1fr;
  }
}
```

## 22.4 Производительные анимации

### Выбор свойств для анимации

Любая анимация должна проектироваться с учётом Rendering Pipeline.

| Приоритет | Свойства | Стадия | Пример |
|-----------|----------|--------|--------|
| ✅ Лучше всего | `transform`, `opacity` | Composite | `scale(1.1)`, `translateX(100px)`, `opacity(0.5)` |
| ⚠️ С осторожностью | `filter`, `clip-path`, `box-shadow` | Paint | `blur(10px)`, `clip-path: circle(50%)` |
| ❌ Избегать | `width`, `height`, `margin`, `top`, `left` | Layout | `width: 200px`, `height: 100px` |

### Пример: производительная анимация

```css
/* ✅ Хорошо — только Composite */
@keyframes slide-in {
  from {
    transform: translateX(-100%);
    opacity: 0;
  }
  to {
    transform: translateX(0);
    opacity: 1;
  }
}

.element {
  animation: slide-in 0.5s ease;
}
```

```css
/* ❌ Плохо — Layout на каждом кадре */
@keyframes slide-in-bad {
  from {
    left: -100%;
    opacity: 0;
  }
  to {
    left: 0;
    opacity: 1;
  }
}

.element {
  animation: slide-in-bad 0.5s ease;
  position: relative;
}
```

### Scroll-driven Animations и View Transitions

Современные анимационные API также должны использовать производительные свойства.

```css
/* ✅ Хорошо — Scroll-driven с transform/opacity */
@keyframes reveal {
  from {
    transform: translateY(50px);
    opacity: 0;
  }
  to {
    transform: translateY(0);
    opacity: 1;
  }
}

.card {
  animation: reveal linear;
  animation-timeline: view();
  /* Только Composite */
}
```

## 22.5 Управление композитными слоями

### Как браузер создаёт слои

Браузер автоматически создаёт композитные слои для:

```text
Элементов с анимацией transform/opacity
  ↓
Элементов с will-change: transform/opacity
  ↓
Элементов с 3D-трансформациями
  ↓
Элементов с video, canvas, WebGL
  ↓
Элементов с z-index + position
  ↓
Элементов с overflow: hidden + clip
```

### will-change — помощь браузеру

Иногда разработчик может помочь движку заранее.

```css
.card {
  will-change: transform;
}
```

### Современный подход

Однако современный подход значительно отличается от рекомендаций десятилетней давности.

Сегодня считается хорошей практикой:

```text
Использовать will-change временно
  ↓
Только перед началом анимации
  ↓
Удалять после завершения
  ↓
Не назначать десяткам элементов одновременно
```

```css
/* ✅ Хорошо — временное использование */
.element {
  transition: transform 0.3s ease;
}

.element:hover {
  will-change: transform;
  transform: scale(1.1);
}

/* ❌ Плохо — постоянное */
.element {
  will-change: transform;
  transform: scale(1);
}
```

### Стоимость слоёв

Избыточное количество слоёв само по себе способно ухудшить производительность.

```text
Каждый слой → потребляет видеопамять
  ↓
Сложность композиции → растёт с числом слоёв
  ↓
Может ухудшить FPS
```

## 22.6 Стабильность интерфейса (CLS)

### Почему CLS важен

Высокая производительность — это не только скорость. Не менее важно сохранить визуальную стабильность страницы.

```text
Cumulative Layout Shift (CLS)
  ↓
Измеряет неожиданные смещения элементов
  ↓
Отрицательно влияет на пользовательский опыт
  ↓
Входит в Core Web Vitals
```

### Основные причины Layout Shift

```text
Изображения без размеров
  ↓
Поздняя загрузка шрифтов
  ↓
Динамическое добавление контента
  ↓
Реклама
  ↓
Встроенные виджеты
```

### Инструменты борьбы с CLS

**1. `aspect-ratio` — резервирование места для изображений**

```css
.image {
  aspect-ratio: 16 / 9;
  width: 100%;
  object-fit: cover;
}
```

**2. `contain-intrinsic-size` — резервирование для content-visibility**

```css
.long-list-item {
  content-visibility: auto;
  contain-intrinsic-size: 200px; /* Резервируем место */
}
```

**3. Font Metrics Overrides — уменьшение скачков текста**

```css
@font-face {
  font-family: 'CustomFont';
  src: url('custom-font.woff2') format('woff2');
  size-adjust: 100%;
  ascent-override: 90%;
  descent-override: 20%;
  line-gap-override: 10%;
}
```

**4. `min-height` для динамического контента**

```css
.dynamic-content {
  min-height: 200px; /* Резервируем место */
}
```

## 22.7 Производительность современных возможностей CSS

### Практические рекомендации

Новые возможности CSS сами по себе не являются «дорогими». Однако каждая имеет свои особенности.

| Возможность | Практические рекомендации |
|-------------|---------------------------|
| **Container Queries** | Использовать свободно, область перерасчёта локализована контейнером |
| **`:has()`** | Избегать чрезмерно сложных селекторов внутри (`:has(.a .b .c)`) |
| **`@scope`** | Позволяет уменьшить влияние глобального каскада |
| **`@layer`** | Практически не влияет на производительность |
| **CSS Nesting** | Не оказывает заметного влияния (работает через `:is()`) |
| **Scroll-driven Animations** | Предпочтительнее JavaScript-анимаций (вычисление в движке) |
| **View Transitions** | Использовать как прогрессивное улучшение |
| **OKLCH / color-mix()** | Незначительное влияние на Style Recalculation |

### Пример: производительный компонент

```css
@layer components {
  @scope (.product-card) {
    .product-card {
      /* ✅ Container Query — локализован */
      container-type: inline-size;
      
      /* ✅ :has() — простой селектор */
      &:has(> img) {
        padding: 0;
      }
      
      /* ✅ CSS Nesting — без влияния на производительность */
      & .title {
        font-size: var(--font-size-xl);
      }
      
      /* ✅ OKLCH + color-mix — современные цветовые модели */
      &:hover {
        background: color-mix(in oklch, var(--surface), black 5%);
      }
    }
  }
}
```

**Большинство возможностей Modern CSS 2026 можно применять без опасений, если соблюдать архитектурные рекомендации предыдущих глав.**

## 22.8 Профилирование вместо преждевременной оптимизации

### Принцип измерения

Современная производительность начинается не с оптимизации, а с измерений.

```text
Измерить
  ↓
Локализовать проблему
  ↓
Оптимизировать
  ↓
Проверить результат
```

### Основные инструменты

```text
Chrome DevTools Performance
  ↓
Запись и анализ всех стадий
  ↓
Performance Insights
  ↓
Автоматические рекомендации
  ↓
Layers
  ↓
Анализ композитных слоёв
  ↓
Rendering
  ↓
Визуализация перерисовок
  ↓
Lighthouse
  ↓
Автоматический аудит
  ↓
Core Web Vitals
  ↓
LCP, FID, CLS, INP
  ↓
Web Vitals Extension
  ↓
Мониторинг в реальном времени
```

### Как анализировать производительность

**Шаг 1: Запись в Performance**

```text
Запустить запись
  ↓
Выполнить действие
  ↓
Остановить запись
  ↓
Найти жёлтые/красные блоки
```

**Шаг 2: Анализ стадий**

```text
Style Recalculation — слишком много правил?
  ↓
Layout — слишком большой DOM?
  ↓
Paint — слишком сложные эффекты?
  ↓
Composite — слишком много слоёв?
```

**Шаг 3: Оптимизация**

```text
Локализовать проблемный компонент
  ↓
Применить соответствующие стратегии
  ↓
Проверить результат
```

**Прежде чем изменять CSS, следует определить:**

- что именно занимает время;
- какая стадия Rendering Pipeline становится узким местом;
- действительно ли проблема связана с CSS, а не с JavaScript или сетью.

## 22.9 Практический чек-лист

### Перед выпуском проекта

Перед выпуском проекта полезно проверить следующие вопросы:

**Архитектура:**
- [ ] Компоненты изолированы (`@layer`, `@scope`, Container Queries)?
- [ ] Используются Design Tokens вместо магических чисел?
- [ ] Каскад управляется через `@layer`, а не через специфичность?

**Ограничение вычислений:**
- [ ] Используется `content-visibility` для длинных страниц?
- [ ] Применяется `contain` там, где компоненты независимы?
- [ ] Задан `contain-intrinsic-size` для элементов с `content-visibility`?

**Анимации:**
- [ ] Анимации построены на `transform` и `opacity`?
- [ ] `will-change` используется только временно?
- [ ] Scroll-driven анимации используют производительные свойства?

**Стабильность:**
- [ ] Для изображений задан `aspect-ratio`?
- [ ] Для веб-шрифтов настроены Font Metrics Overrides?
- [ ] Минимальная высота задана для динамического контента?

**Профилирование:**
- [ ] Производительность проверена в DevTools?
- [ ] Core Web Vitals в зелёной зоне?
- [ ] CLS < 0.1?

## 22.10 Итоги главы

1. **Оптимизация начинается с архитектуры** — изоляция компонентов, локальный каскад

2. **`contain`** — изоляция области пересчёта

3. **`content-visibility`** — пропуск рендеринга вне viewport

4. **`contain-intrinsic-size`** — резервирование места (борьба с CLS)

5. **Минимизация Layout** — Flexbox/Grid, `transform`, `aspect-ratio`

6. **Производительные анимации** — `transform` и `opacity` (Composite)

7. **Управление слоями** — `will-change` только временно

8. **CLS** — `aspect-ratio`, `contain-intrinsic-size`, Font Metrics Overrides

9. **Современные возможности** — безопасны при правильной архитектуре

10. **Профилирование** — измерение вместо предположений

---

**Главная мысль:** Современная оптимизация CSS — это прежде всего вопрос архитектуры. Изоляция компонентов, локализация областей перерасчёта, использование контейнерных запросов, `content-visibility`, `contain` и композитных анимаций позволяют значительно сократить объём работы браузера без усложнения кода. Вместо борьбы с последствиями производительных проблем современный CSS предлагает проектировать интерфейсы так, чтобы дорогостоящие этапы Rendering Pipeline выполнялись как можно реже, а решения принимались на основе измерений, а не предположений.
